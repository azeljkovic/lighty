# Errors and logging

The request types expose two important behavior switches:

- `throwOnHttpError` controls non-OK HTTP responses.
- `logger` controls built-in or custom request logging.

## HTTP errors

By default, a response with `ok === false` is returned as a `RequestResult`, so tests can assert its status and body.

```ts
const result = await client.getRequest("/missing");

if (result.status === 404) {
  console.log(result.data);
}
```

## Throwing non-OK responses

Set `throwOnHttpError: true` to throw `HttpRequestError` after the response body has been parsed:

```ts
import {HttpRequestError, patchRequest} from "@azeljkovic/lighty";

try {
  await patchRequest("https://api.example.test/users/1", {
    body: {
      email: "",
    },
    throwOnHttpError: true,
  });
} catch (error) {
  if (error instanceof HttpRequestError) {
    console.log(error.status);
    console.log(error.statusText);
    console.log(error.headers);
    console.log(error.body);
    console.log(error.url);
  }
}
```

The error body uses the same parser selected by `responseType` or automatic parsing.

`HttpRequestError<TBody>` exposes `status`, `statusText`, `headers`, `body`, and
`url`. The exported `HttpRequestErrorOptions<TBody>` describes those constructor
options when you need to type an error wrapper or helper.

This setting can be defined on `ClientConfig` and overridden per request. Set it
back to `false` on a request when a client normally throws but that request
needs to assert a non-OK response.

## Invalid JSON

When a response is parsed as JSON and parsing fails, `lighty` throws `InvalidJsonResponseError`.

This happens when:

- `responseType` is `"json"`, or
- `responseType` is omitted and the media type is `application/json` or ends
  in `+json`, such as `application/problem+json`.

The error includes:

- `status`
- `statusText`
- `headers`
- `body`, containing the raw response text
- `url`
- `cause`, containing the original JSON parse error

`InvalidJsonResponseErrorOptions` is also exported for code that needs to type
the constructor options. It includes the same fields as the error plus `cause`.

## Failure behavior

lighty only wraps HTTP status failures and invalid JSON. Other failures preserve
their original error so callers can use the platform or application-specific
error type.

| Situation | Result | Logging behavior |
| --- | --- | --- |
| Non-OK response with `throwOnHttpError: false` (the default) | Resolves with `RequestResult`. | Normal completion hooks run. |
| Non-OK response with `throwOnHttpError: true` | Rejects with `HttpRequestError` after parsing the body. | `requestEnd` receives an error summary. |
| JSON parsing fails | Rejects with `InvalidJsonResponseError`. | `requestEnd` receives an error summary. |
| Network failure, caller abort, or timeout | Rejects with the error from `fetch` or the abort mechanism; lighty does not wrap it. | `requestEnd` receives an error summary after a request has started. |
| `responseParser` throws or rejects | Rejects with the original parser error. | `requestEnd` receives an error summary. |
| `requestStart` logger hook throws or rejects | Rejects with the original hook error before `fetch` is called. | No `requestEnd` hook runs. |
| `response` logger hook throws or rejects | Rejects with the original hook error. | `requestEnd` receives an error summary. |
| `requestEnd` logger hook throws or rejects | Rejects with the original hook error; it can replace an earlier request error. | No later hook runs. |

The `response` hook is only called for a verbose logger. See [Logger
configuration](#logger-configuration) for the hook levels.

## Redirects

`redirect` is passed directly to `fetch`.

```ts
const result = await client.getRequest("/redirect-to", {
  redirect: "manual",
  responseType: "text",
  params: {
    url: "/login",
    status_code: 302,
  },
});
```

Supported values are:

```ts
type RequestRedirectMode = "error" | "follow" | "manual";
```

## Logger configuration

`logger` accepts a `RequestLoggerConfig`:

```ts
type RequestLoggerLevel = "off" | "basic" | "verbose";
type RequestLoggerConfig = RequestLoggerLevel | false | RequestLogger;
```

Built-in levels:

| Level | Behavior |
| --- | --- |
| `basic` | Logs request start and request completion. |
| `verbose` | Logs request start, parsed response details, and request completion. |
| `off` | Disables logging. This is the default when `logger` is omitted. |
| `false` | Also disables logging. |

Enable basic logging for a request:

```ts
await client.getRequest("/users", {
  logger: "basic",
});
```

## Custom logger hooks

```ts
const events: unknown[] = [];

await client.postRequest("/users", {
  body: {
    username: "ada",
    password: "secret",
  },
  logger: {
    level: "verbose",
    requestStart: (entry) => events.push(["requestStart", entry]),
    response: (entry) => events.push(["response", entry]),
    requestEnd: (entry) => events.push(["requestEnd", entry]),
  },
});
```

Logger hooks can be synchronous or asynchronous.

## Logger hook entries

The custom logger type and event entry types are exported for typed integrations:

```ts
import type {
  RequestEndLogEntry,
  RequestLogger,
  RequestStartLogEntry,
  ResponseLogEntry,
} from "@azeljkovic/lighty";
```

| Hook | Entry type | Fields |
| --- | --- | --- |
| `requestStart` | `RequestStartLogEntry` | `method`, redacted `url`, redacted `headers`, and optional redacted `body`. |
| `response` | `ResponseLogEntry` | Request fields plus `status`, `statusText`, `ok`, `redirected`, response `type`, redacted headers, and redacted body. |
| `requestEnd` | `RequestEndLogEntry` | `method`, redacted `url`, `durationMs`, optional `status`, optional `ok`, and an optional error summary. |

`RequestLogger` exposes the optional `level`, `requestStart`, `response`, and
`requestEnd` hooks. A custom logger emits `response` only when its level is
`"verbose"`; `requestStart` and `requestEnd` run unless the level is `"off"`.

## Redaction

Before data reaches logger hooks, `lighty` redacts sensitive values from:

- Header names containing terms such as `authorization`, `cookie`, `password`, `secret`, `session`, `token`, or `apiKey`.
- Query parameter names containing sensitive terms.
- Body object keys containing sensitive terms, recursively.

The redacted value is:

```text
[REDACTED]
```
